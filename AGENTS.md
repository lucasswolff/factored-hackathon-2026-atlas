## Working rules

- Keep supplied facts, team-created offer/policy, and mock actions visibly distinct. `campaign_sends.had_conversion` is not a verified product contract; do not claim historical campaign-to-acquisition attribution or causal A/B lift.
- The offer catalog and eligibility policy are not supplied. Use a versioned, explicitly synthetic offer and deterministic policy service. The conversation model may explain policy output but must not invent lending rules or approve credit. A mock application is `PENDING_REVIEW`, not a real acquisition.
- Use a server-bound test session for personalized fixture fields and enforce fixture ownership in the service/tool layer. A campaign link, send ID, customer number, or national ID alone is not authentication. In the browser demo, explicit selection on the “Choose a demo customer” screen enables use of that fixture's profile; there is no additional profile permission button. This is not real authentication. The hosted judge app is public and contains only team-generated fictional fixtures; protect the reviewer queue separately. Require consent before the simulated precheck and explicit confirmation before mock application creation; verify any action by reading back the stored outcome.
- Keep credentials out of files, logs, commits, public submissions, and external model requests. The Snowflake SQL files must remain trackable and retain `<...>` credential placeholders. Do not paste supplied AWS keys into them.
- `data/` contains local CSVs from the same AWS source already loaded to Snowflake. `snowflake/` contains all-`VARCHAR` landing tables; validate and cast fields in curated views or downstream code. Preserve raw data and document lineage. Avoid committing generated copies of large CSVs or customer-level outputs.
- Supplied transcripts are Spanish and repetitive; Portuguese cases and varied product questions must be team-created and labeled. Evaluate a learned component against a baseline on held-out cases and report failures as well as successes.
- The [tone pairs](data/derived/tone_examples_es_pt.json) are team-translated versions of repetitive Spanish transcript templates, awaiting bilingual review. They are a style reference, not product facts or training ground truth.
- The intended judge demo lets a visitor click a supplied campaign card mapped to one team-created named offer, or start a direct conversation. Both paths go through “Choose a demo customer” before chat; this is a scenario selector, not a login. The click is a new simulated event, not a selected historical clicked send. All three countries are in scope; income is in local currency. Suggestions and prechecks are for selected fixtures only; the UI persona choice permits profile use, while the CLI retains an explicit profile-permission step. Anonymous self-reported income cannot trigger a suggestion. The English card names are Campus, Horizon, Rewards, and Summit, with the same core benefits across countries. Campus is student-only; the supplied `Student` segment is not verified enrollment. Rewards is the mid-tier card, with fewer travel benefits than Summit. The local UI is runnable, but the end-to-end MVP is not. Historical clicks can be backtested as engagement; synthetic prequalification on current customer snapshots is a retrospective simulation, not an approval backtest.
- For human routing, match language and credit specialty first, verify assignment, and use accent only as an optional customer preference. Typed chat does not establish accent.
- Build the end-to-end service before optional campaign A/B work. Historical template comparisons are descriptive because random assignment and a clean holdout are not recorded.

## Before calling the prototype complete

Run relevant tests and held-out evaluation, verify normal/ambiguous/human paths in Spanish and Portuguese, test unauthorized access and tool failures, and update the plan with measured results and limitations. The organizer's [problem statement](docs/factored_docs/problem_statement.pdf) is the source of truth for submission requirements.
